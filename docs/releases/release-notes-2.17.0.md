## Firely CQL SDK 2.17.0

> [!WARNING]
> **.NET 8 support ends on 10 November 2026.** Microsoft's .NET 8 reaches
> [End of Support](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/) on that date, and
> CQL SDK 2.x support for .NET 8 ends with it — see
> [discussion #1426](https://github.com/FirelyTeam/firely-cql-sdk/discussions/1426) for the full
> announcement. This release still ships `net8.0` alongside `net10.0`; plan your move to .NET 10
> (Microsoft's current LTS) before that date. Progress on removing the target is tracked in
> [#1427](https://github.com/FirelyTeam/firely-cql-sdk/issues/1427).

### tl;dr

> **Upgrading?** Here is the short version:
>
> - **Breaking changes:** The CQL-to-ELM translator applies the quantity in `X within Q of Y` with a point `Y`, and writes 1-based, end-inclusive `locator` strings; packaging embeds the ELM JSON a library was read from as its `application/elm+json` attachment instead of re-serializing it; the compiler no longer merges duplicate definitions in hand-edited ELM.
> - **Required migrations:** Re-verify measure output — a large number of fixes in this release move CQL evaluation results. Re-package to pick up the code generator fixes: `GeneratorToolVersion` moves `6.0.0.0` → `6.0.3.0`, inside the invoker's `[6.0.0.0, 7.0.0.0)`, so artifacts packaged with 2.16.0 keep loading. If you reference the Firely .NET SDK directly, move it to `6.8.0` in the same step.
> - **Highlights:** Packaging is several times faster: the `dqm-content-qicore-2025` library set packages in about a fifth of the time, at about a third of the peak memory. The QICore and US Core model infos now ship with the SDK.

### Generated Code Compatibility

- `LibrarySetCSharpCodeGenerator.GeneratorToolVersion`: **`6.0.0.0` → `6.0.3.0`** (patch).
- Accepted by `LibraryInstanceInvoker_6_0`, whose supported range is `[6.0.0.0, 7.0.0.0)`.

Every step stays inside the invoker's range, so libraries generated by 2.16.0 load and run unchanged. Regenerate checked-in `*.g.cs` and packaged FHIR `Library` resources with embedded C# or assemblies to pick up the code generator fixes the new version carries: `6.0.1.0` keeps a list of value-typed elements widened to `List<Any>` instead of evaluating it to `null` (#1712), `6.0.2.0` reads a narrowed FHIR primitive's `value` as the System type the model declares (#1721), and `6.0.3.0` writes generated C# with LF line endings on every platform (#1760).

### CQL SDK

#### New Public API

- `Hl7.Cql.CqlToElm.Toolkit.CqlModel.QICore411`, `USCore311`, `QICore600` and `USCore610`, which select the bundled QICore and US Core model infos — see Improvements. (#1805)
- `Hl7.Cql.Packaging.Toolkit.ElmAttachmentFormatting` (`Passthrough`, `Indented`, `Compact`) and `PackagingToolkitConfig.ElmAttachmentFormatting`, which set the whitespace of a packaged library's ELM attachment — see CQL Packager. (#1715)

#### Improvements

- **CQL-to-ELM translator** — the QICore 4.1.1 and 6.0.0 and US Core 3.1.1 and 6.1.0 model infos ship with the SDK, embedded in `Hl7.Cql.Model`, so a library declaring `using QICore version '6.0.0'` (or one of the other three) translates without supplying the model info yourself. They are opt-in: select them through the new `CqlModel` members in `CqlToolkitConfig.Models`, or by name in the Packager's `Cql:Models` setting. The default model set is unchanged. A bundled model info is deserialized only when selected, but the `Hl7.Cql.Model` package grows by the size of the four XML files (about 3 MB uncompressed). A type is identified by its model's url and name without a version, so a `CqlToolkit` configured with two versions of the same model now throws `ArgumentException` at construction, naming the model and versions, where it failed on the first type lookup before. Translate libraries written against another version with a separate toolkit. (#1740, #1805)

#### Dependency Updates

- `FirelyNetVersion`: `6.6.0` → `6.7.0` (#1814) → `6.8.0` (#1825), bumping `Hl7.Fhir.Base` and `Hl7.Fhir.R4` for every package that consumes Firely .NET SDK types (`Hl7.Cql.Fhir`, `Hl7.Cql.Packaging`, `Hl7.Cql.Packager`) and for the demo projects. A consumer with its own direct reference to the Firely .NET SDK should move it to `6.8.0` as well. `Hl7.Fhir.Base` has the same dependencies at all three versions, so no other package version moves with it. No public API, generated C# output, or CQL evaluation result changes with it. The two behavior changes in Firely .NET SDK `6.8.0` do not reach the CQL SDK: the runtime's FHIR-to-CQL date and time conversions do not read the fraction-digit count that `Hl7.Fhir.ElementModel.Types.DateTime` now keeps from parsing, and the SDK does not call the FHIRPath conversion functions, which now return empty or `false` for a complex type instead of throwing.

#### Potentially Breaking

- **CQL-to-ELM translator — `X within Q of Y` with a point `Y` is membership in the interval from `Y - Q` to `Y + Q`** (open when `properly` is given), as the specification defines it. The quantity was ignored and `X` was tested against the point interval `[Y, Y]`, so **CQL evaluation results change for every `within` phrase with a point on the right**. The closed form also carries the specification's `and Y is not null` guard, so a `within` of a null point yields `false` rather than `true`, and `properly within` yields `null`. `occurs within` and `aggregate … starting <quantity>` translate instead of throwing. (#1730, #1754)
- **CQL-to-ELM translator — `locator` strings follow the reference translator's convention.** Characters are 1-based, the span runs from the first character of the first token through the last character of the last token (on the line that character is on, also when a string or quoted identifier spans lines), and a single-character span is written `line:char`. The start was 0-based and the end was the start of the last token. Anything that reads the `locator` strings of ELM this translator produces sees different values. (#1725, #1756)
- **Compiler — the `AmbiguousOverloadCorrector` preprocessing step is removed.** It is observable only for hand-edited ELM in which one library defines the same expression twice, or the same function twice with identical operand types: such ELM is no longer silently reduced to a single definition. A duplicated expression fails to compile. A duplicated function fails where it is called, if that call has no result type and the compiler has to resolve it: as an ambiguous call when the function has other overloads, otherwise when the library's definitions are indexed. A call that already carries its result type still compiles, with the second definition skipped and a warning logged. The Java translator never emits such definitions, and none of the reference ELM corpora contains them. (#1746, #1767)

#### Fixes

Many of the entries below **change CQL evaluation results**. See the Upgrade Checklist.

**Interval and list operators**

- **Runtime — the interval relationship operators share one model of a boundary without a value**, and decide a result as soon as one boundary comparison settles it. This covers `before`, `after`, `starts`, `ends`, `includes`, `properly includes`, `properly included in`, `same as`, `same or before`, `same or after`, `overlaps`, `overlaps before`, `overlaps after`, `meets`, `meets before`, `meets after` and `in`. (#1699)
  - A closed null boundary is the minimum or maximum of the point type in every operator, so a point that matches that extreme only at a coarser precision (`@9999` against a closed null high, `@0001` against a closed null low) is decided instead of unknown.
  - An open null boundary is unknown, but the other boundary can still settle the result: `5 in Interval(null, 3]`, `0 after Interval[1, null)`, `9 before Interval(null, 3]`, `Interval[1, 10] includes Interval(null, 20]`, `Interval[1, 5] same as Interval[7, null)` and `Interval(null, 3] properly includes 5` are `false` instead of `null`. The unknown boundary ranges over the values its interval permits, so `1 in Interval[1, null)` and `Interval[null, 7] properly includes 5` are `true` instead of `null`.
  - `meets`, `meets before` and `meets after` hold when the first interval ends immediately before the second starts. An end equal to the start is a shared point, so `Interval[1, 5] meets Interval[5, 9]` is `false` instead of `true`. For Date, DateTime and Time the predecessor or successor is taken at the value's own precision and compared at the requested precision, so `Interval[@2023-01-01, @2023-06-01] meets month Interval[@2023-07-01, @2023-10-01]` stays `true`. Boundaries without a value are decided from what they stand for: `Interval[1, null] meets Interval[5, null]` is `false` and `Interval[null, 4] meets Interval[5, null]` is `true` instead of `null`, and `Interval[1, 5] meets Interval(null, 9]` is `null` instead of `false`.
  - The point forms of `properly includes` and `properly included in` apply the specification's rule for every point type: the interval includes the point and is not a unit interval containing only the point. A point at a boundary of a wider interval is properly included, so `1 properly included in Interval[1, 5]` and `Interval[@T12:00:00.000, @T21:59:59.999] properly includes @T12:00:00.000` are `true` instead of `false`; the four conformance cases that expect `false` are skipped, see [cqframework/cql-tests#152](https://github.com/cqframework/cql-tests/issues/152). A point whose unit is incommensurable with the boundaries' (`5 'm' properly included in Interval[1 'kg', 10 'kg']`) is `null` instead of `true`.
- **Runtime — `overlaps before`, `overlaps after`, `properly includes` and `properly included in` decide an unknown (open null) boundary over the values it can take**, so a result that no value of the boundary can satisfy is `false` instead of `null`: `Interval[1, 1] overlaps after Interval[0, null)`, `Interval[0, 0] properly includes Interval(null, null)` and `Interval(null, 2] properly includes Interval[null, 2]` are `false`. Results that some values satisfy and others do not stay `null`. (#1704, #1706)
- **Runtime — the singleton overloads of the list operators `properly includes` and `properly included in` return `false` for a null list**, as `contains` and `in` do, instead of `null`: `null as List<String> properly includes 'a'` is `false`. The list-list overloads keep returning `null` for a null argument. (#1705, #1707)

**Arithmetic, dates and quantities**

- **Runtime — `Date` and `DateTime` plus or minus a quantity more precise than the value convert the quantity to the value's precision first**, truncating, as the "Add" and "Subtract" sections of "Date and Time Operators" require. The quantity was applied at its own precision and only the result was truncated. The conversion uses the calendar durations the specification lists for equivalence (12 months per year, 365 days per year, 30 days per month, 7 days per week, then 24, 60, 60 and 1000). So `Date(2014) - 25 months` is `@2012` (was `@2011`), `Date(2014,6) - 33 days` is `@2014-05` (was `@2014-04`), `Date(2014,6) + 60 days` is `@2014-08` (was `@2014-07`) and `DateTime(2016) + 365 days` is `@2017T` (was `@2016T`). A quantity at or above the value's precision is applied as before, and `Time` arithmetic is unchanged. (#1771, #1772)
- **Runtime — `ConvertQuantity` between `'a'` and `'mo'` returns the correct value**: `ConvertQuantity(1 'a', 'mo')` is `12 'mo'` (was `0.0833… 'mo'`) and `ConvertQuantity(12 'mo', 'a')` is `1 'a'` (was `144 'a'`). (#1785, #1787)
- **Runtime — `Ceiling` and `Floor` of a Decimal whose result is outside the Integer range return `null`**, as §9.B "Arithmetic Operators" requires, instead of throwing `OverflowException`: `Ceiling(2147483648.2)` and `Floor(-2147483649.2)` are `null`. Results at either end of the Integer range are unchanged. (#1762, #1763)
- **Translator, code generator and runtime — ratio literals compile and run, and ratio comparisons follow the specification.** A ratio selector such as `1 'mg':2 'mL'` stopped C# generation with "Operator Ratio is not supported yet", and a ratio of unitless quantities such as the titre `1:128` failed translation; such a quantity now takes the default unit `'1'`. Equality compares numerator with numerator and denominator with denominator, so `1:8 = 2:16` is `false`, and a comparison with an unknown part is `null` unless the other part differs. Equivalence compares the ratios the two represent, with unit conversion, so `1:100 ~ 10:1000` is `true`; a ratio that cannot be divided (a zero denominator or a null part) is equivalent to no ratio. `Distinct`, `Union` and `Except` deduplicate equal ratios. Generated C# and evaluation results of existing libraries are unchanged, since ratio comparisons previously failed to compile or threw. (#1778)
- **Runtime (FHIR type converter) — a FHIR `Ratio` converts to the CQL `Ratio` type.** `FhirTypeConverter` converted a CQL `Ratio` to a FHIR `Ratio` but not back, so a `Parameters` parameter whose value is a `Ratio` could not be converted to a `CqlRatio`, and ELM that hands the compiler a FHIR `Ratio` where a `System.Ratio` is required failed to compile. A FHIR `Ratio` missing either part, or holding a part without a value, converts to `null`. Libraries that convert through `FHIRHelpers.ToRatio` are unaffected. (#1779)

**Type conversion and code generation**

- **Code generator — `as` from a list of value-typed elements to a list of a reference element type keeps the list.** `{ 1, 2, 3 } as List<Any>` evaluated to `null`; such a list is now boxed element-wise for both `as` and `cast as`. `=`, `!=` and `~` of two `List<Any>` operands built from such lists compare the lists instead of a `null`. The reverse direction is unchanged. This raised `GeneratorToolVersion` to `6.0.1.0`. (#1711, #1712)
- **Code generator — a FHIR primitive's `value` is read as the System type the model declares** even where the expression expects a wider type. After narrowing a choice with `is`, such as `when R is FHIR.dateTime then R.value` in a `case` over `Condition.onset`, the value evaluated to the `FhirDateTime` itself instead of a `System.DateTime`. This raised `GeneratorToolVersion` to `6.0.2.0`. (#1719, #1721)
- **Code generator — generated C# is written with LF line endings** rather than the host platform's, so the same inputs produce the same output on Windows and on Unix, including the C# embedded in a packaged FHIR `Library`. This raised `GeneratorToolVersion` to `6.0.3.0`. (#1759, #1760)
- **Compiler — `aggregate distinct` compiles when the query's items are not of the aggregate's result type**, such as over a multi-source query, whose items are tuples. `Distinct` is applied to the query's items, as the specification requires, where it failed with `CannotBindToCqlOperatorError`. Queries that compiled before are unchanged. (#1774, #1776)

**CQL-to-ELM translator**

- **The branches of `if` and `case`, and the elements of a list selector, get the one type they share**, the way the reference translator types them: an implicit conversion where one exists (`Integer` and `Decimal` become `Decimal`, `Date` and `DateTime` become `DateTime`, `Interval<Date>` and `Interval<DateTime>` become `Interval<DateTime>`, `Code` and `Concept` become `Concept`), and a choice of the branch types only when none does. Any two different branch types produced a choice type, after which operators such as `start of`, `in` and `overlaps` over the conditional failed to resolve. A list selector with a declared element type (`List<Decimal>{ 1, 2 }`) converts its elements to that type, and a `case` whose branches are all `null` is typed `Any`. The static type of such expressions in the emitted ELM changes accordingly. (#1731, #1764)
- **A generic system function called with arguments that leave its type parameter unbound**, such as `Coalesce` over arguments typed `Any`, binds the parameter to `Any` and continues, instead of ending translation of the library with an `ArgumentException`. (#1798, #1801)
- **An instance selector that sets a list-typed element whose model info declares a nested element type**, such as `ClaimResponse { adjudication: … }`, translates instead of ending with a `NullReferenceException`. (#1729, #1753)
- **A grammar construct the translator does not implement is reported as an error** (`Translation of <rule> '<source text>' is not implemented.`) on a `Null` node typed `Any`, instead of ending translation with a `NullReferenceException`. This covers `%x` external constants and code and concept selectors with a `display` clause. (#1728, #1755)
- **A call no overload applies to, or that is ambiguous, is typed `Any`** after its error is reported, so expressions over it no longer report a second error against the type of an arbitrary candidate. (#1732, #1765)
- **Every `CqlToElmError` carries `startLine`, `startChar`, `endLine` and `endChar`**, taken from the node it is reported on or the closest enclosing node with a locator; library-level errors, such as a duplicate definition name, take the position of the offending definition. The year, month, day, time and timezone parts of date, date/time and time literals carry the exact span of that part. (#1725, #1756)
- **The type-mismatch diagnostic names the expected and found types the right way round**, and no longer ends in a stray quotation mark. (#1750, #1752, #1768)

### CQL Packager

#### Breaking

- **Packaging (`PackagingToolkit` and Packager CLI) — the ELM embedded as the `application/elm+json` attachment of a packaged FHIR `Library` is the JSON the library was read from**, instead of being rebuilt from the ELM object graph. The attachment therefore keeps empty collections such as `annotation` and `signature`, and no longer gains the normalizations serialization applied — `accessLevel` written out explicitly, and `resultTypeSpecifier` derived from a legacy `type` discriminator. Parsing either form through this SDK yields an equivalent library, since those corrections are applied on load. The new `Packaging:ElmAttachmentFormatting` setting (`PackagingToolkitConfig.ElmAttachmentFormatting`) controls the attachment's whitespace: `Passthrough` (the default, byte-identical to the source file apart from line endings), `Indented` or `Compact`. (#1714, #1715)

#### Improvements

- **Packaging is several times faster.** ELM files load in parallel; libraries compile in parallel in dependency order; FHIR resources are built in parallel, with concurrency capped at four, so peak memory does not grow with core count; each library's direct data requirements are computed once and reused by every library that includes it (#1686, #1690). Packaging no longer re-serializes every ELM library to embed it as an attachment, and no longer compiles the library set three times when a library legitimately produces no assembly (#1714, #1715). Packaging `dqm-content-qicore-2025` (166 ELM libraries) through to FHIR with the Packager CLI went from about 207 s to 44 s, and its peak working set from about 2.4 GB to 0.9 GB, measured against 2.16.0 on a 32-core machine.
- **Packaged attachments no longer depend on the platform or checkout.** Every text attachment on a packaged FHIR `Library` — the CQL, the generated C# and the ELM — has its line endings normalized to LF, so a working tree checked out with CRLF and one checked out with LF produce the same resources. (#1717, #1759, #1760)
- **A library whose included libraries are available only as ELM is packaged**, such as one including FHIRHelpers loaded from its published ELM. An ELM library without matching CQL is a reference library: it is not packaged itself, but it resolves the includes of the packaged libraries, its Retrieves count towards their data requirements, and the packaged library refers to it by canonical in a `depends-on` related artifact. `AddPackagingInputs(cqlToolkit, elmToolkit)` dropped such ELM, and `ConvertToFhirResources` skipped every library that included it with only a warning. In the Packager CLI likewise, an ELM file without a matching CQL file no longer causes the libraries that include it to be skipped. (#1816, #1817)

### Upgrade Checklist

1. **Re-verify measure output.** A large number of fixes in this release move CQL evaluation results — interval boundary semantics and `meets`, `within` with a point, date arithmetic with a finer quantity, `ConvertQuantity` between years and months, `Ceiling`/`Floor` overflow and `List<Any>` widening among them. Treat moved scores for affected measures as expected rather than as new defects. The `within` change takes effect when CQL is translated with this SDK's translator.
2. **Re-package to pick up the code generator fixes.** Libraries generated by 2.16.0 still load, since the invoker accepts `[6.0.0.0, 7.0.0.0)`, but they keep the behavior of the old generator. Regenerate checked-in `*.g.cs` and packaged FHIR `Library` resources with embedded C# or assemblies.
3. **If you reference the Firely .NET SDK directly, move it to `6.8.0`** in the same step as this upgrade: `Hl7.Cql.Fhir` `2.17.0` declares `Hl7.Fhir.Base >= 6.8.0`, so a lower direct pin is a package downgrade.
4. **If you read `locator` strings** from ELM this SDK's translator produced, expect 1-based, end-inclusive spans.
5. **If you compare packaged ELM attachments byte for byte**, expect the ELM JSON the library was read from. Set `Packaging:ElmAttachmentFormatting` (or `PackagingToolkitConfig.ElmAttachmentFormatting`) to `Indented` or `Compact` to reformat it.
6. **If you hand-edit ELM, remove duplicate definitions**, which the compiler no longer merges silently.
7. **If you are on `net8.0`, plan the move to `net10.0`** — see the warning at the top of this document.

### Common Items To Check

- PublicAPI shipped/unshipped promotions: 10 entries promoted, 4 in `Cql.CqlToElm` and 6 in `Cql.Packaging`. No removals and no signature changes.
- New or changed exception types: `Ceiling` and `Floor` return `null` where they threw `OverflowException`; a `CqlToolkit` configured with two versions of one model throws `ArgumentException` at construction.
- Public runtime/operator API changes: none. `ICqlOperators` is unchanged.
- Generator version and invoker range: stated above under `### Generated Code Compatibility`; the generator moved, the range did not.

Vonk moves to `6.8.0` as part of adopting this release, and must do so in the same step as bumping `FirelyCqlVersion`, since `Hl7.Cql.Fhir` `2.17.0` declares `Hl7.Fhir.Base >= 6.8.0` and Vonk pins `Hl7.Fhir.Base` directly.
- Packager CLI argument changes: no command-line arguments change. The configuration gains `Packaging:ElmAttachmentFormatting`, and `Cql:Models` accepts `USCore311`, `QICore411`, `USCore610` and `QICore600`; the example `Hl7.Cql.Packager.appsettings.json` carries both.
