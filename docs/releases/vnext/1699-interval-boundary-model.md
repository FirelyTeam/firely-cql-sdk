## Fixes

- The interval relationship operators (`before`, `after`, `starts`, `ends`, `includes`, `properly includes`, `properly included in`, `same as`, `same or before`, `same or after`, `overlaps`, `overlaps before`, `overlaps after`, `meets`, `meets before`, `meets after` and `in`) share one model of what a boundary without a value stands for, and decide a result as soon as one boundary comparison settles it. The following results change (#1699):
  - A closed null boundary is the minimum or maximum of the point type in every operator, so a point that matches that extreme only at a coarser precision (`@9999` against a closed null high, `@0001` against a closed null low) is decided instead of unknown.
  - An open null boundary is unknown, but the other boundary can still settle the result: `5 in Interval(null, 3]`, `0 after Interval[1, null)`, `9 before Interval(null, 3]`, `Interval[1, 10] includes Interval(null, 20]`, `Interval[1, 5] same as Interval[7, null)` and `Interval(null, 3] properly includes 5` are `false` instead of `null`. The unknown boundary ranges over the values its interval permits, so `1 in Interval[1, null)` and `Interval[null, 7] properly includes 5` are `true` instead of `null`.
  - `meets`, `meets before` and `meets after` hold when the first interval ends immediately before the second starts, in either form the specification gives: the end is the predecessor of the start, or the start is the successor of the end. An end equal to the start is a shared point, so `Interval[1, 5] meets Interval[5, 9]` is `false` instead of `true`. For Date, DateTime and Time the predecessor or successor is taken at the value's own precision and compared at the requested precision, so `Interval[@2023-01-01, @2023-06-01] meets month Interval[@2023-07-01, @2023-10-01]` and `Interval[@2012-01-07, @2012-01-14] meets month Interval[@2012-01, @2012-01-25]` stay `true`. Boundaries without a value are decided from what they stand for instead of returning `null` (`Interval[1, null] meets Interval[5, null]` is `false`, `Interval[null, 4] meets Interval[5, null]` is `true`) or a flat `false` (`Interval[1, 5] meets Interval(null, 9]` is `null`, `Interval[1, 5] meets Interval(null, 3]` is `false`).
  - The point forms of `properly includes` and `properly included in` apply the specification's rule for every point type: "this operator returns true if the interval contains (i.e. includes) the point, and the interval is not a unit interval containing only the point". A point at a boundary of a wider interval is properly included, so `1 properly included in Interval[1, 5]` and `Interval[@T12:00:00.000, @T21:59:59.999] properly includes @T12:00:00.000` are `true` instead of `false`; the four conformance cases that expect `false` are skipped, see [cqframework/cql-tests#152](https://github.com/cqframework/cql-tests/issues/152). A point whose unit is incommensurable with the boundaries' (`5 'm' properly included in Interval[1 'kg', 10 'kg']`) is `null` instead of `true`.

This changes CQL evaluation results for the affected expressions.
