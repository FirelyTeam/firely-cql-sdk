## Fixes

- The interval relationship operators (`before`, `after`, `starts`, `ends`, `includes`, `properly includes`, `properly included in`, `same as`, `same or before`, `same or after`, `overlaps`, `overlaps before`, `overlaps after`, `meets`, `meets before`, `meets after` and `in`) share one model of what a boundary without a value stands for, and decide a result as soon as one boundary comparison settles it. A closed null boundary is the minimum or maximum of the point type in every operator, so a point that matches that extreme only at a coarser precision (`@9999` against a closed null high, `@0001` against a closed null low) is decided instead of unknown. An open null boundary is unknown, but the other boundary can still settle the result: `5 in Interval(null, 3]`, `Interval(null, 3] properly includes 5`, `0 after Interval[1, null)`, `9 before Interval(null, 3]` and `Interval[1, 10] includes Interval(null, 20]` are `false` instead of `null`. `meets`, `meets before` and `meets after` answer from the boundaries when both highs or both lows have no value instead of returning `null`: `Interval[1, null] meets Interval[5, null]` is `false`, `Interval[null, 4] meets Interval[5, null]` is `true`, and `Interval[1, null) meets Interval[5, null)` stays `null`; against an unknown boundary they return `null` or a definite answer from its range instead of `false`. `same as` decides from the boundaries too, so an unknown boundary that cannot coincide with the other interval's gives `false` instead of `null` (`Interval[1, 5] same as Interval[7, null)`). The point forms of `properly includes` and `properly included in` are decided from the boundaries as well, so `Interval(null, 3] properly includes 3` is `false` instead of `null` and `Interval[null, 7] properly includes 5` is `true` instead of `null`. (#1699)

This changes CQL evaluation results for the affected expressions.
