## Firely CQL SDK 2.18.0

> [!WARNING]
> **.NET 8 support ends on 10 November 2026.** Microsoft's .NET 8 reaches
> [End of Support](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/) on that date, and
> CQL SDK 2.x support for .NET 8 ends with it — see
> [discussion #1426](https://github.com/FirelyTeam/firely-cql-sdk/discussions/1426) for the full
> announcement. This release still ships `net8.0` alongside `net10.0`; plan your move to .NET 10
> (Microsoft's current LTS) before that date. Progress on removing the target is tracked in
> [#1427](https://github.com/FirelyTeam/firely-cql-sdk/issues/1427).

### tl;dr

> **Upgrading?** Here is the short version:
>
> - **Breaking changes:**
>   - **Runtime** — `CqlUcumYearArithmeticError` and `CqlUcumMonthArithmeticError` move to `Hl7.Cql.Primitives.Errors`, and `CqlPointFromNonUnitIntervalError` moves to `Hl7.Cql.Operators.Errors` in `Hl7.Cql.Runtime`. Code that names them must be changed and recompiled.
>   - **Runtime** — a membership test against a value set that cannot be resolved throws `CqlException<CqlUnresolvedValueSetError>` instead of answering `false`. A context created without a value set dictionary now throws for every value set it is asked about.
>   - **Runtime** — a string, or a code without a system, tested against a value set of several code systems throws `CqlException<CqlAmbiguousStringInValueSetError>`.
>   - **Runtime** — errors the specification signals are thrown as `CqlException<TError>` instead of .NET exceptions: invalid `Date`, `DateTime` and `Time` components, a unit that is not temporal in date and time arithmetic, `expand` by a fractional `per`, and `singleton from` on a list of several elements.
>   - **Runtime** — `=` on Concepts compares the display and the order of the codes, and `~` on Concepts requires a shared code.
>   - **Runtime** — `CqlQuantity.TryParse`, `CqlRatio.TryParse`, the date and time parsers and `FhirTypeConverter`'s string conversions accept only the formats of the CQL `To*` conversions.
>   - **Runtime** — `ICqlOperators` gains three members, which a custom implementation must add.
>   - **Invocation toolkit** — `ReadCqlAssemblyInfo` reports an assembly that references newer assemblies than the host has as not supported.
> - **Required migrations:**
>   1. Re-verify measure output: a large number of fixes in this release move CQL evaluation results.
>   2. Give the context's value set dictionary, or the `ValueSetSource`, every value set the libraries reference, or attach a terminology service.
>   3. Where you catch `ArgumentException`, `ArgumentOutOfRangeException`, `OverflowException`, `NotSupportedException` or `InvalidOperationException` around evaluation, catch `CqlException` instead, or `catch (CqlException e) when (e.Error is ICqlEvaluationError)`.
>   4. Update the namespace of the three moved error types wherever you name them, and recompile.
>   5. Upgrade runtime and generated content together: libraries generated by 2.17.0 load on 2.18.0, but what 2.18.0 packages needs a 2.18.0 runtime (`GeneratorToolVersion` `6.1.0.0` → `6.2.2.0`).
> - **Highlights:**
>   - An exception thrown during evaluation names the CQL definition it was thrown in (`CqlException.EvaluationFrames`), and `ICqlEvaluationError` tells an error the specification signals from a failure inside the SDK.
>   - Arithmetic, aggregates and conversions whose result cannot be represented evaluate to `null`, as the specification requires, instead of ending evaluation with a .NET exception.
>   - The translator resolves an include from an ELM library (`CqlToolkit.AddReferenceLibraries`), such as FHIRHelpers loaded from its published ELM.
>   - `ToRatio`, `ConvertsToRatio` and `ToQuantity` of a ratio are supported, and libraries without a version, or with a version such as `1.0.0-draft`, compile.

### Generated Code Compatibility

- `LibrarySetCSharpCodeGenerator.GeneratorToolVersion`: **`6.1.0.0` → `6.2.2.0`** (minor).
- Accepted by `LibraryInstanceInvoker_6_0`, whose supported range is `[6.0.0.0, 7.0.0.0)`.

Every step stays inside the invoker's range, so libraries generated by 2.17.0 load and run unchanged. Each step makes the generator handle CQL it failed on before:

- `6.2.0.0`: C# generated for `ToRatio` calls the new `ICqlOperators.ConvertStringToRatio`. (#1777, #1781)
- `6.2.1.0`: a library without a version, or with a version that is not numeric, compiles. The generated class always carries the two-argument `[CqlLibrary]`, with `null` for a missing version. (#1846, #1849)
- `6.2.2.0`: a non-strict `as` whose operand is a value cast to a choice or to `Any` compiles when the value's own type cannot be the target, and evaluates to `null`. (#1869, #1879)

For a library that compiled with 2.17.0, the generated C# is unchanged apart from the version in its `GeneratedCode` attribute, so regenerating is needed only for libraries that failed before. Do not ship what 2.18.0 generates to a host on an earlier SDK: a library compiled by 2.18.0 references the 2.18.0 SDK assemblies, and C# that calls `ToRatio` needs `ICqlOperators.ConvertStringToRatio`, which earlier runtimes lack.

### CQL SDK

#### New Public API

- **Runtime** — `ICqlEvaluationError`, in `Hl7.Cql.Exceptions`, marks the errors the CQL specification requires to be signalled to the calling environment during evaluation. `ICqlArithmeticError` now derives from it, and `CqlPointFromNonUnitIntervalError` implements it. A host tells an evaluation error from a failure inside the SDK with `catch (CqlException e) when (e.Error is ICqlEvaluationError)`. (#812, #1845)
- **Runtime** — `CqlException.EvaluationFrames` lists the CQL definitions that were being evaluated when the exception was thrown, innermost first, as `CqlEvaluationFrame` values with `LibraryName`, `LibraryVersion` and `DefinitionName`. The extension `CqlErrorExtensions.GetCqlEvaluationFrames(Exception)` reads the same frames from any other exception thrown during evaluation, such as one from a data source. (#812, #1845)
- **Runtime** — new `ICqlEvaluationError` values, each carried by a `CqlException<TError>` where a .NET exception was thrown or an answer was given before — see Potentially Breaking:
  - `Hl7.Cql.Operators.Errors.CqlInvalidDateTimeComponentsError`, with the `Type` and the components it was given (`Year` to `Millisecond`, `TimezoneOffset`). (#1786)
  - `Hl7.Cql.Operators.Errors.CqlExpandFractionalPerError`, with `PerValue`, `PerUnit` and `PointType`. (#1786)
  - `Hl7.Cql.Primitives.Errors.CqlUnsupportedTemporalUnitError`, an `ICqlArithmeticError` in `HL7.Cql.Abstractions`, with the quantity's `Unit` and the CQL `Type` of the value. (#1789)
  - `Hl7.Cql.Operators.Errors.CqlSingletonFromMultipleElementsError`, with `ElementCount` and `ElementType`. (#1818, #1819)
  - `Hl7.Cql.ValueSets.Errors.CqlUnresolvedValueSetError`, with the canonical of the value set that could not be resolved in `ValueSetUri`. (#1521, #1858, #1865, #1877)
  - `Hl7.Cql.ValueSets.Errors.CqlAmbiguousStringInValueSetError`, with the value set in `ValueSetUri` and the code tested in `Code`. `ValueSetUri` is `null` only for an `InMemoryValueSet` tested on its own, which does not know its canonical URI. (#1866, #1878)

  All but `CqlUnsupportedTemporalUnitError` are in `Hl7.Cql.Runtime`.
- **Runtime** — `ICqlOperators.ConvertStringToRatio(string?)`, `ICqlOperators.ConvertsToRatio(object?)` and `ICqlOperators.ConvertRatioToQuantity(CqlRatio?)`. (#1777, #1781)
- **Runtime** — the `display` parameter of both `CqlConcept` constructors defaults to `null`, so `new CqlConcept(codes)` creates a concept without a display (#1808, #1856). The `codes` parameter of the `CqlConcept(IReadOnlyList<CqlCode>?, string?)` constructor defaults to `null`, so `new CqlConcept()` and `new CqlConcept(display: "x")` create a concept without codes; the `CqlConcept(IEnumerable<CqlCode>?, string?)` constructor still requires its codes, so neither call is ambiguous (#1857, #1875). The parameter types are unchanged, so code compiled against an earlier version is unaffected.
- **CQL-to-ELM translator** — `CqlToolkit.AddReferenceLibraries(IEnumerable<Library>)`, which takes ELM libraries that the translated CQL libraries include — see Improvements. (#1833, #1834)
- **Invocation toolkit** — `Hl7.Cql.Invocation.Toolkit.Errors.CqlAssemblyWithNewerReferenceError`, a new `ICqlAssemblyInfoError`, is the `CqlAssemblyInfo.ReadError` of an assembly that references a newer version of an assembly than the host has. It names the assembly (`AssemblyName`), the referenced assembly (`ReferencedAssemblyName`), the version referenced (`ReferencedVersion`) and the host's version (`HostVersion`). (#1830, #1838)

#### Improvements

- **CQL-to-ELM translator (`CqlToolkit`)** — `AddReferenceLibraries` takes ELM libraries that the translated CQL libraries include, such as FHIRHelpers loaded from its published ELM. The translator resolves an include from such a reference library when the toolkit holds no CQL for it, reading the names, access levels and result types of its definitions and the operand types of its functions from the ELM. A library whose include is available only as ELM then translates without an "Unable to resolve library" error for it, so the errors left in its ELM are its own. A reference library is not translated itself, a CQL library with the same identifier takes precedence over it, one whose identifier has a system is included by its qualified name (`system.id`), and a statement whose ELM declares no result type cannot be referenced. Translation without reference libraries is unchanged. (#1833, #1834)
- **Runtime** — the message of a `CqlException` thrown during evaluation ends with the definition it was thrown in, for example "Thrown while evaluating definition 'Point' of library 'Inner' version '1.0.0'." A function without operands has a frame of its own, like a definition; a function with operands has one only when the host invokes it directly, and is otherwise reported as the definition that called it. A sequence that a definition returns unread, such as a retrieve from a data source that reads lazily, is reported by the definition that reads it, or without frames when the host reads it. Generated C# and `GeneratorToolVersion` are unchanged. (#812, #1845)
- **Runtime** — the remarks of `ICqlArithmeticError` gave a catch clause that never matches; they now give `catch (CqlException e) when (e.Error is ICqlArithmeticError)`. (#1845)
- **Runtime** — `CompositeDataSource.Retrieve` returns a fully evaluated list, as `BundleDataSource.Retrieve` does. Each source's retrieve is called once per retrieve, and reading the result again, as a cached definition or a cross join does, no longer calls the sources again. A failure in a source surfaces from the retrieve itself, in the definition that retrieves. A source that returns its results lazily is now read in full on each retrieve. (#1847, #1848)

#### Dependency Updates

- None. `FirelyNetVersion` stays at `6.8.0`.

#### Breaking

- **Runtime — three error types move out of `Hl7.Cql.Primitives`** into the `Errors` namespace of the area that throws them, where the SDK's other error types are (#1844, #1854):
  - `Hl7.Cql.Primitives.CqlUcumYearArithmeticError` is now `Hl7.Cql.Primitives.Errors.CqlUcumYearArithmeticError`, still in `HL7.Cql.Abstractions`.
  - `Hl7.Cql.Primitives.CqlUcumMonthArithmeticError` is now `Hl7.Cql.Primitives.Errors.CqlUcumMonthArithmeticError`, still in `HL7.Cql.Abstractions`.
  - `Hl7.Cql.Primitives.CqlPointFromNonUnitIntervalError` is now `Hl7.Cql.Operators.Errors.CqlPointFromNonUnitIntervalError`, in `Hl7.Cql.Runtime` instead of `HL7.Cql.Abstractions`.

  Code that names one of them, such as `catch (CqlException<CqlUcumYearArithmeticError> e)`, adds `using Hl7.Cql.Primitives.Errors;` or `using Hl7.Cql.Operators.Errors;`, or spells out the new full name, and is recompiled. An assembly compiled against an earlier version does not find the old types. A host that catches `CqlException` with `when (e.Error is ICqlEvaluationError)` needs no change.
- **Runtime — `CqlPointFromNonUnitIntervalError` is no longer a positional record.** Its constructor is `internal`, it has no `Deconstruct`, and `Low`, `High`, `LowClosed` and `HighClosed` are get-only. Code that deconstructed it reads the properties instead. (#1844, #1854)

#### Potentially Breaking

**Errors the specification signals**

- **Runtime — errors the specification signals to the calling environment are thrown as `CqlException<TError>` instead of .NET exceptions.** A host that catches `ArgumentException`, `ArgumentOutOfRangeException`, `OverflowException`, `NotSupportedException` or `InvalidOperationException` around evaluation no longer catches these errors. Catch `CqlException` instead, or `catch (CqlException e) when (e.Error is ICqlEvaluationError)` for every error the specification signals. Generated C# and `GeneratorToolVersion` are unchanged.
  - The `DateTime` operator given a timezone offset outside `-13.00` to `14.00` hours, or one that is not a whole number of minutes, throws `CqlException<CqlInvalidDateTimeComponentsError>` instead of returning a DateTime with another offset (`24` became `+00:00`, and `0.001` was truncated to `+00:00`). (#1786)
  - The `Date`, `DateTime` and `Time` operators given components that do not form a value of the type (a year outside 0001 to 9999, a month outside 1 to 12, a component given below one that is not, a timezone offset that cannot be represented) throw `CqlException<CqlInvalidDateTimeComponentsError>` instead of `ArgumentException`, `ArgumentOutOfRangeException` or `OverflowException`. (#1786)
  - `expand` of an Integer or Long interval, or a list of them, by a `per` with a decimal portion (such as `expand { Interval[10, 10] } per 0.1`) throws `CqlException<CqlExpandFractionalPerError>` instead of `NotSupportedException`: the specification makes those points Decimal, which these overloads cannot return. (#1786)
  - `+` and `-` of a Date, DateTime or Time and a quantity whose unit is not a time-valued unit of that type (such as `1 'cm'`, `1 'hour'` added to a Date, or `1 'year'` added to a Time), and `expand` of a Date, DateTime or Time interval, or a list of them, by a `per` whose unit is not temporal (such as `per 1 'cm'`), throw `CqlException<CqlUnsupportedTemporalUnitError>` instead of `ArgumentException`. (#1789)
  - `singleton from` on a list with more than one element throws `CqlException<CqlSingletonFromMultipleElementsError>` instead of the `InvalidOperationException` of LINQ's `SingleOrDefault`. The error itself is unchanged: the specification requires it in §9.B, section "Singleton From". (#1818, #1819)

**Value sets**

- **Runtime (`Hl7.Cql.Fhir`) — `ValueSetSource` signals an error for a membership test against a value set it cannot resolve:** one that was not added to it, that its resource resolver does not find, while no terminology service is attached. It throws `CqlException<CqlUnresolvedValueSetError>` where it returned `false`, an answer that could not be told apart from a code that is not in the value set. The specification requires the error in §9.B, section "In (Valueset)": "If the value set reference cannot be resolved, a run-time error is thrown." This reaches every membership test made through a `ValueSetSource`: the `in` operators on a code, string, concept or list of them, and a retrieve filtered by a value set, such as `[Condition: "Diabetes"]`, as soon as a resource with a code is tested against it. A value set the source holds or resolves answers as before, and so does an attached terminology service. (#1521, #1858)
  - **Who sees a difference:** a host that evaluates CQL referencing a value set it did not give its `ValueSetSource`, for example one built with `ToValueSetDictionary` from only some of the value sets its libraries use. A membership test against such a value set was `false`; the evaluation now ends with the error.
  - **What to do:** give the `ValueSetSource` every value set the libraries reference, through `Add` or its resource resolver, or attach a terminology service. The error is an `ICqlEvaluationError` and names the value set in `ValueSetUri`.
- **Runtime — `HashValueSetDictionary` signals an error for a membership test against a value set that was not added to it**, with the same `CqlException<CqlUnresolvedValueSetError>`, where it returned `false`. `HashValueSetDictionary` is also the dictionary a context uses when the host passes none to `FhirCqlContext.ForBundle` or `FhirCqlContext.WithDataSource`, so **a context created without value sets now signals the error for every value set it is asked about**. This reaches the same membership tests as above. A value set the dictionary holds answers as before. Expanding a value set to its codes, as `ExpandValueSet` or a value set used as a `List<Code>` does, still gives no codes for a value set the dictionary does not hold, since the specification does not make that an error. (#1865, #1877)
  - **Who sees a difference:** a host that evaluates CQL referencing a value set without giving the context a value set dictionary, or giving it a `HashValueSetDictionary` that lacks the value set.
  - **What to do:** give the context a value set dictionary that holds every value set the libraries reference, such as a `HashValueSetDictionary` filled through `Add`, or a `ValueSetSource`.
- **Runtime — testing a code without a code system for membership in a value set that holds codes from more than one code system signals an error.** The String overload of `in (Valueset)`, such as `'1234' in "Some Value Set"`, matched the string against the codes of every system and answered `true` when any of them had it; it throws `CqlException<CqlAmbiguousStringInValueSetError>` instead. The specification requires the error in §9.B, section "In (Valueset)": "if the resolved value set contains codes from multiple code systems, a run-time error is thrown because the operation is ambiguous." The runtime tests a `Code` without a system the same way as a string, so `Code { code: '1234' } in "Some Value Set"`, and a `Concept` or list holding such a code, signal the error too. Every value set dictionary of the SDK behaves the same: `HashValueSetDictionary`, `ValueSetSource`, and an `InMemoryValueSet` tested on its own. `ValueSetSource` cannot tell for a value set that only its terminology service knows, and leaves that test to the service. Code systems are told apart ignoring case, and a code of the value set that has no system does not count as a code system of its own. A value set of one code system answers as before, and a `Code` that names its system is not affected. (#1866, #1878)
  - **Who sees a difference:** a library that tests a string, or a code without a system, against a value set whose codes come from more than one code system, such as one that mixes SNOMED CT and ICD-10-CM codes. The test answered `true` or `false`; the evaluation now ends with the error.
  - **What to do:** test a `Code` that names its system, or use a value set of one code system.

**Concepts**

- **Runtime — `=` on Concepts compares the display as well as the codes**, by the tuple equality semantics the specification gives it: its `EqualIsFalse` example, two concepts with the same codes and the displays `'Concepts'` and `'More Concepts'`, is `false` instead of `true`. The codes compare as a list does, in order, so concepts with the same codes in a different order are not equal. When the two specify different components, such as codes or a display on one side only, the result is `null` instead of `true` or `false`; it stays `null` when either concept is null. A concept without codes is a concept rather than null, so two concepts without codes are equal exactly when their displays are, instead of always. (#1876, #1880)
- **Runtime — `~` on Concepts is `true` only when the two share an equivalent code**, so concepts without codes, or with an empty list of codes, are not equivalent to each other, nor to themselves. The display is still ignored, `null ~ null` is still `true`, and a concept is still not equivalent to null. (#1876, #1880)
- **Runtime — the operations that match list elements by equality follow `=` on Concepts:** `distinct`, `union`, `except`, `intersect`, `in`, `contains`, `IndexOf`, `includes`, `Mode` and `=` on lists of Concepts no longer treat concepts as the same when they differ in their display or in the order of their codes, or when they have no codes and different displays. A Concept element of a tuple compares as a Concept. A tuple, and a list inside a tuple or a list, is equivalent to another only when their elements are: no longer merely because the elements are equal as .NET values, or because both sides hold the same list. A tuple or list that holds a Concept without codes, or a ratio whose denominator is zero, is therefore not equivalent to an equal one, even when both sides hold one shared list, such as the result of one definition or of two identical list selectors, which the generated C# evaluates once. (#1876, #1880)
  - **Who sees a difference:** a library that compares Concepts, or deduplicates or matches lists of them, notably FHIR `CodeableConcept` values. FHIR gives the order of a concept's codings no meaning, but CQL's list equality does, so two such concepts with the same codings in a different order are no longer equal, and `distinct`, `union` and the other operations above can now keep both.
  - **What to do:** to compare FHIR concepts regardless of the order of their codings, or of their display, use `~`, which asks only for a shared equivalent code.

**Parsing and conversion**

- **Runtime — the public parsers behind the string conversions take the formats and ranges those conversions follow** (see Fixes), so they now reject strings they parsed and accept strings they rejected. `CqlQuantity.TryParse` takes the format of `ToQuantity`: a quantity without a unit gets the unit `'1'` (`CqlQuantity.TryParse("5")` now succeeds with `5 '1'`), while a unit that is not quoted at both ends (`"5 mg"`, `"444 'cm"`) or is empty, and a value with a group separator or a leading decimal point, are rejected. `CqlRatio.TryParse` takes each quantity as `CqlQuantity.TryParse` does, with no whitespace around a quantity or the colon (`" 5 : 2 "` is rejected). `CqlDateTime.TryParse`, `CqlTime.TryParse`, `DateTimeIso8601.TryParse` and `TimeIso8601.TryParse` return false for an hour, minute, second or timezone offset out of range, the offset's range being `-13:00` to `+14:00`, instead of throwing `ArgumentOutOfRangeException` or accepting the value; the two date-time parsers also return false for a date time whose instant in UTC falls outside `0001-01-01` to `9999-12-31`, instead of throwing. The string conversions of `ICqlOperators.Convert<T>` to `CqlQuantity`, `CqlDateTime` and `CqlTime` use these parsers and change with them. (#1839, #1860)
  - **Who sees a difference:** a host that calls one of these parsers, or `ICqlOperators.Convert<T>` from a string, on its own input. The signatures are unchanged, so nothing fails to compile or load, but a string such as `"5 mg"` or `"2014-01-01T10:00:00-13:30"` that parsed now gives false, and `CqlQuantity.TryParse("5")` now succeeds.
  - **What to do:** give these parsers strings in the formats the CQL specification gives the `To*` conversions: quote a quantity's unit (`5 'mg'`) and leave no whitespace around the quantity, and keep a timezone offset within `-13:00` to `+14:00`. A `catch (ArgumentOutOfRangeException)` around `CqlDateTime.TryParse` or `DateTimeIso8601.TryParse` is no longer needed: they return false instead.
- **Runtime (`Hl7.Cql.Fhir`) — `FhirTypeConverter` converts a string to an Integer, Long or Decimal only in the format that `ToInteger`, `ToLong` and `ToDecimal` accept**, `(+|-)?#0` and `(+|-)?#0(.0#)?`, and gives `null` for any other string, as those operators do. It parsed with .NET's `NumberStyles.Integer` and `NumberStyles.Number` under the invariant culture, so it accepted whitespace around the number (`Convert<int?>(" 1 ")` gave `1`), group separators (`Convert<decimal?>("1,000.25")` gave `1000.25`, and `Convert<decimal?>("12,34")` gave `1234`), a trailing sign (`"1.5-"`), a decimal point without a digit on both sides (`".5"`, `"1."`) and trailing NUL characters. Each of these now gives `null`. A FHIR primitive such as an `Integer`, `FhirDecimal` or `Quantity` converts from the value it holds, as before, so FHIR data is unaffected, and CQL evaluation results do not change: a CQL expression converts a String with the `To*` operators themselves, never through the converter. (#1868, #1885)
  - **Who sees a difference:** a host that converts its own strings to numbers through `FhirTypeConverter.Default`, a converter from `FhirTypeConverter.Create`, or `ICqlOperators.Convert<T>`. The signatures are unchanged, so nothing fails to compile or load, but a string in one of the forms above gives `null` where it gave a number.
  - **What to do:** hand these conversions numbers in the CQL format: trim surrounding whitespace and leave out group separators. Parse a number written for a particular culture, such as `12,34`, in the host before handing it over.
- **Runtime (`Hl7.Cql.Fhir`) — an exclusive boundary of an `Interval<DateTime>` without a timezone offset converts to a FHIR `Period` boundary at the converter's default timezone offset**, which is the evaluation request's unless `FhirCqlContextOptions.OverrideConverterTimezoneOffset` sets another. It used to convert at UTC, while the inclusive boundary of the same interval already took the default. A `Period` is inclusive at both ends, so the converter steps an exclusive boundary inward by one unit of its precision, and that step gave the value an explicit UTC offset. Under an evaluation request at `+02:00`, the measurement period `Interval[@2024-01-01T00:00:00.0, @2025-01-01T00:00:00.0)` converted to a `Period` ending at `2024-12-31T23:59:59.999Z`, two hours after the period ends. It now ends at `2024-12-31T23:59:59.999+02:00`. A stepped boundary on 0001-01-01 or 9999-12-31 that cannot carry the default keeps UTC, as an unstepped boundary does. Under a UTC evaluation request the output is unchanged. This changes the FHIR the SDK emits for such intervals; CQL evaluation results are unchanged. (#1507, #1855)

**Public API**

- **Runtime — `ICqlOperators` gains `ConvertStringToRatio`, `ConvertsToRatio` and `ConvertRatioToQuantity`** without default implementations, so a custom `ICqlOperators` implementation must add all three. (#1777, #1781)
- **Runtime — `ILibrary.Version`, `CqlLibraryAttribute.Version` and the `Version` parameter of `CqlLibraryAttribute`'s constructor are declared `string?`**, since a library can have no version. Compiled code is unaffected. Code that reads them with nullable warnings enabled may get a new warning. (#1846, #1849)
- **Invocation toolkit — `InvocationToolkit.ReadCqlAssemblyInfo` reports an assembly that references a newer version of an assembly than the host has as not supported.** It compares each assembly the read assembly references with the host's assembly of the same name: the one the default load context has loaded, or else the one its trusted platform assemblies list, such as the SDK's, the Firely .NET SDK's and the .NET runtime's. Such an assembly read as supported before. It now reads with `IsSupported` false and `HasReadErrors` true, a `CqlAssemblyWithNewerReferenceError` as its `ReadError`, and no libraries listed. That covers a `+dll` packaged by a later release of the SDK, which references that release's assemblies, and one compiled on a newer .NET than the host runs. A reference to an assembly the host does not have, such as the assembly of an included library, is still left to the load. (#1830, #1838)
  - **Who sees a difference:** any host that reads `IsSupported` or `HasReadErrors`, such as one that rejects FHIR `Library` attachments it cannot run. Through the default load context the toolkit could not load these assemblies anyway: `CreateLibrarySetInvoker` failed for the whole library set they were added to. A host whose own resolver binds older copies of the referenced assemblies could load them, though, and now sees them reported as not supported, with no libraries listed.
  - **What to do:** treat `CqlAssemblyWithNewerReferenceError` like any other `ReadError`. A host whose own resolver binds those references can still add the assembly with `AddAssemblyBinaries` and load it; the reader no longer lists its libraries, though.

#### Fixes

Many of the entries below **change CQL evaluation results**. See the Upgrade Checklist. Unless an entry says otherwise, the generated C# and `GeneratorToolVersion` are unchanged.

**Results that cannot be represented**

- **Runtime** — operations whose result cannot be represented evaluate to `null` instead of ending evaluation with a .NET exception, as the specification's arithmetic rule requires ("operations that cause arithmetic overflow or underflow, or otherwise cannot be performed (such as division by 0) will result in null, rather than a run-time error"). One set of guarded arithmetic and conversion helpers replaces the per-operator overflow handling, and each overflow is reported as a warning through the message event. The following results change (#1786):
  - `+` and `-` of a Date or DateTime and a calendar quantity (`year`, `month`, `week`, `day`) whose value is outside the Integer range, or whose number of weeks in days is outside the Decimal range: `null` instead of `OverflowException`.
  - `+` and `-` of two quantities whose units differ, where converting a value to the other unit leaves the Decimal range: `null` instead of `OverflowException`.
  - `*`, `/` and `div` of quantities, where the product or quotient (directly or after unit conversion) leaves the Decimal range: `null` instead of `OverflowException`.
  - `+` and `-` of two quantities in the same unit whose result leaves the Decimal range: `null` instead of a quantity without a value.
  - `mod` of quantities whose units differ, where converting the divisor leaves the Decimal range: `null` instead of `OverflowException`.
  - `*` of two Decimals, and `/` and `div` of two Decimals, whose result leaves the Decimal range: `null` instead of `OverflowException`.
  - `div` of the minimum Integer or Long by `-1`: `null` instead of `OverflowException`.
  - `mod` of the minimum Integer or Long by `-1`: `0` instead of `OverflowException`.
  - `Ceiling`, `Floor` and `Truncate` of a Decimal outside the Integer range: `null` instead of `OverflowException`.
  - `Exp` whose result exceeds the Decimal range, and `Ln(0)`: `null` instead of `OverflowException`.
  - `Round` with a negative precision: `null` instead of `ArgumentOutOfRangeException`; with a precision above 28: the argument unchanged instead of `ArgumentOutOfRangeException`.
  - `ConvertQuantity` and `CanConvertQuantity` where the converted value leaves the Decimal range: `null` and `false` instead of `OverflowException`.
  - Comparisons of quantities whose units differ (`=`, `<`, `>`, `between`, and the interval operators `before`, `after`, `meets`, `overlaps`, `includes`, `contains`, `except`, `same or before`, `same or after` over quantity intervals), where a canonical value leaves the Decimal range: unknown (`null`, or `false` for equivalence) instead of `OverflowException`.
  - `expand` of an Integer, Long or Decimal interval by a `per` beyond the type's range, and of a Date or DateTime interval by a `per` of weeks beyond the Decimal range in days: the partitions that fit instead of `OverflowException`.
- **Runtime** — Integer and Long results that wrapped around silently are `null` instead: `*` of two Integers or two Longs whose product leaves the range, and `Abs` of the minimum Integer or Long. (#1786)
- **Runtime** — `duration between` and `difference between` of DateTimes in minutes, seconds or milliseconds whose count exceeds the Integer range (for example `duration in milliseconds between` two DateTimes 25 days apart) are `null` instead of `2147483647` or a wrapped negative count. (#1786)
- **Runtime** — `expand` of a Date, DateTime or Time interval, or a list of them, by a `per` below one unit of its precision (such as `per 0.5 years`) is `null`, as for a `per` of zero, instead of never returning: adding the `per` drops its decimal portion, so the partitions did not advance and the result grew without bound. (#1786)
- **Runtime** — `expand` of a Decimal interval, or a list of them, by a `per` too small to change a boundary of that magnitude (such as `per 0.5` on a boundary of 10^28) is `null`, as for a `per` of zero, instead of never returning. (#1786)
- **Runtime** — `*` and `/` of two Decimals whose nonzero result is too small to represent (such as `0.0000000000000000000000000001 * 0.1`), and the quantity and `GeometricMean` results built on them, are `null` instead of `0`; `div` of such operands is still `0`. (#1786)
- **Runtime** — aggregate operators whose result cannot be represented evaluate to `null` instead of ending evaluation with a .NET exception or a wrapped value, and report the overflow as a warning through the message event. The following results change (#1788):
  - `Avg` of Decimals whose total leaves the Decimal range: `null` instead of `OverflowException`; whose nonzero mean is too small in magnitude to represent (such as `Avg({ 0.0000000000000000000000000001, 0.0 })`): `null`, as for `/`, instead of `0`.
  - `Product` of Integers or Longs whose product leaves the type's range: `null` instead of the value it wrapped around to.
  - `Product` of Decimals or quantities whose product leaves the Decimal range: `null` instead of `OverflowException`; whose product of nonzero values is too small in magnitude to represent: `null`, as for `*`, instead of `0`.
  - `Product` of quantities whose units differ: `null`, with a warning as `Sum` gives, instead of `NotSupportedException`.
  - `Median` of Decimals whose two middle values sum beyond the Decimal range (such as `Median({ maximum Decimal, maximum Decimal })`): their midpoint instead of `OverflowException`.
  - `StdDev` and `Variance` whose result leaves the Decimal range: `null` instead of `OverflowException`.
  - `StdDev` and `Variance` whose nonzero result is too small in magnitude to represent as a Decimal (such as the `StdDev` of four zeroes and `0.0000000000000000000000000001`): `null` instead of `0`.
  - `StdDev` and `Variance` of a single value: `null`, as for any division by zero, instead of `OverflowException`.
  - `StdDev` and `Variance` of quantities whose units differ: `null`, with a warning, instead of `NotSupportedException`.
  - `PopulationStdDev` and `PopulationVariance` where the total of the values, a deviation from their mean or its square leaves the Decimal range: `null` instead of `OverflowException`; whose nonzero variance is too small in magnitude to represent: `null` instead of `0`.
- **Runtime** — `Exp` and `Power` whose nonzero result is too small in magnitude to represent as a Decimal (such as `Exp(-100)` or `Power(2.0, -100)`) evaluate to `null`, with a warning, instead of `0`, as `*` and `/` do. (#1788)
- **Runtime** — `ConvertQuantity` (`convert ... to`) to a unit the quantity cannot be converted to (such as `convert 1 'mg' to 'mL'`) is `null`, reported as a warning through the message event, as the specification requires ("Otherwise, the result is null"), instead of `ArgumentException`. (#1789)

**Conversions**

- **CQL-to-ELM translator, code generator and runtime** — `ToRatio(String)`, `ConvertsToRatio(Any)` and `ToQuantity(Ratio)` are available. `ToRatio` and `ConvertsToRatio` used to fail CQL-to-ELM translation as unknown functions, and `ToQuantity` on a ratio failed C# generation. `ToRatio('1.0 \'mg\':2.0 \'mg\'')` is `1.0 'mg':2.0 'mg'`, a quantity without a unit takes the default unit `'1'` (`ToRatio('1:128')` is `1:128`), and a string that is not two quantities separated by a colon is null (`ToRatio('1.0 \'mg\';2.0 \'mg\'')`). `ConvertsToRatio` is true for a ratio and for a string `ToRatio` accepts. `ToQuantity` of a ratio divides the numerator by the denominator, as `/` on quantities does, so `ToQuantity(6 'mg':2 'mL')` equals `3 'mg/mL'` and a zero denominator gives null. `convert '1:2' to Ratio` converts like `ToRatio` instead of throwing "No conversion from System.String to CqlRatio is defined". `CqlRatio.TryParse` accepts the format the specification gives for `ToRatio`: each quantity is an optionally signed number with an optional quoted unit, and a colon inside a quoted unit does not split the ratio. Existing evaluation results are unchanged, since these conversions previously failed to translate, compile or run. This raised `GeneratorToolVersion` to `6.2.0.0`. (#1777, #1781)
- **Runtime** — the `ConvertsToBoolean`, `ConvertsToDate`, `ConvertsToDateTime`, `ConvertsToDecimal`, `ConvertsToInteger`, `ConvertsToLong`, `ConvertsToQuantity`, `ConvertsToString` and `ConvertsToTime` operators follow the CQL specification. Each is true when its argument already is of the target type or the matching `To*` conversion gives a non-null result for it, false for any other argument, and null for null. They used to return false for almost every Boolean, Integer, Long and Decimal argument and for an argument of the target type itself, and true for any string whether or not it converts. `ConvertsToBoolean` of an Integer, Long or Decimal is true only for 0 and 1, and `ConvertsToInteger` of a Long only within the Integer range. Each operator gives the answer of the runtime's matching `To*` conversion, so where that conversion departs from the specification, the operator departs with it: `ConvertsToQuantity` of the string `5 'foo'` is true, because the unit is not yet checked against UCUM (#1782). The change reaches any library that calls these operators, such as ELM from another translator. (#1829, #1836)
- **Runtime** — the `To*` conversions follow the formats and ranges the CQL specification gives them, and return null, never an exception, for an argument outside them. The matching `ConvertsTo*` operators follow, since each gives the answer of its `To*` conversion. The following results change (#1839, #1860):
  - `ToDateTime` of a string whose hour, minute, second or timezone offset is out of range (`ToDateTime('2014-01-01T25:00:00Z')`, `'2014-01-01T10:61:00'`, `'2014-01-01T10:00:00+15:00'`), or whose instant in UTC falls outside `0001-01-01` to `9999-12-31` (`'0001-01-01T00:00:00+01:00'`): null instead of `ArgumentOutOfRangeException`. `ConvertsToDateTime` of such a string is false instead of throwing. The range of the offset is the one Table 5-H gives, `-13:00` to `+14:00`, which the `DateTime` operator enforces too, so an offset more than 13 hours behind UTC (`ToDateTime('2014-01-01T10:00:00-13:30')`, `'2014-01-01T10:00:00-14:00'`) also gives null, instead of a DateTime that `DateTime(2014, 1, 1, 10, 0, 0, 0, -13.5)` refuses.
  - `ToTime` of a string whose hour, minute or second is out of range (`ToTime('25:00:00')`, `ToTime('10:61')`): null instead of a Time holding that component. With an offset outside `-13:00` to `+14:00`: null instead of `ArgumentOutOfRangeException` when it is more than 14 hours from UTC (`'10:00:00+15:00'`), and instead of a Time when it is 13 to 14 hours behind (`'10:00:00-13:30'`).
  - `ToDate` of a date-time string whose components are each in range: its date as written, ignoring the time portion, instead of null. `ToDate('2014-01-01T12:30:00')` is `@2014-01-01`. Since the date does not depend on the offset, the instant the string names in UTC need not fall within `0001-01-01` to `9999-12-31`: `ToDate('0001-01-01T00:00:00+01:00')` is `@0001-01-01` and `ToDate('9999-12-31T23:59:59.999-13:00')` is `@9999-12-31`, while `ToDateTime` of either string is null. A time portion with a component out of range (`ToDate('2014-01-01T25:00:00')`) still gives null.
  - `ToQuantity` of a string accepts the format `(+|-)?#0(.0#)?('<unit>')?`, with spaces allowed only between the value and the unit. A value without a unit gets the unit `'1'` (`ToQuantity('5')` is `5 '1'` instead of null), and the unit may follow the value directly (`ToQuantity('5\'mg\'')` is `5 'mg'` instead of null). A unit that is not quoted at both ends (`ToQuantity('444 \'cm')` was `444 'cm'`, `ToQuantity('5 mg')` was `5 'mg'`) or is empty, a value with a group separator or a leading decimal point, and a space before the value or after the unit give null. The unit is not yet checked against UCUM (#1782).
  - `ToRatio` of a string takes each quantity in exactly the format of `ToQuantity`, as the specification defines it, so whitespace around a quantity or the colon gives null: `ToRatio(' 5 : 2 ')` is null, as `ToQuantity(' 5')` is.
  - `ToDecimal`, `ToInteger` and `ToLong` of a string accept only `(+|-)?#0(.0#)?` and `(+|-)?#0`. Surrounding whitespace (`ToInteger(' 1 ')`), a group separator (`ToDecimal('1,000')`), a trailing sign (`ToDecimal('1-')`) and a leading decimal point (`ToDecimal('.5')`) give null instead of a number.
  - `ToBoolean` of an Integer, Long or Decimal other than 0 and 1 (`ToBoolean(2)`, `ToBoolean(2L)`, `ToBoolean(0.5)`): null instead of false.
  - `ToInteger` of a Long outside the Integer range (`ToInteger(3000000000L)`): null instead of the wrapped value `-1294967296`.
- **Runtime (`Hl7.Cql.Fhir`)** — `FhirTypeConverter` converts a date-time string to a Date as `ToDate` does, ignoring the time portion: `Convert<CqlDate>("2014-01-01T12:30:00")` is `2014-01-01` instead of null. A time portion with a component out of range still gives null. (#1868, #1885)
- **Runtime (`Hl7.Cql.Fhir`)** — converting a FHIR `Code<TEnum>` to its `TEnum?` no longer throws. The conversion that `FhirTypeConverter` registers for every FHIR enumeration read the code's `ObjectValue`, which holds the FHIR literal as a `string` (for example `"female"`), and cast that to the enum, so it always failed with an `InvalidCastException`. It now returns the code's enum value, or `null` when the code has none. `FhirCqlContext` installs this converter in `CqlOperators`, so an evaluation that reached this conversion used to fail and now produces a value. (#1804)

**Dates, times and comparisons**

- **Runtime** — `years between` and `months between` two DateTimes count a year or a month that ends on the anniversary date as whole only once the start's time of day has been reached, as Appendix H of the CQL specification defines a year and a month. `years between @2012-03-10T22:05:09 and @2013-03-10T19:10:03` is `0` instead of `1`, and `months between @2012-03-10T22:05:09 and @2012-04-10T19:10:03` is `0` instead of `1`. The reverse direction mirrors the rule: `years between @2013-03-10T19:10:03 and @2012-03-10T22:05:09` is `0` instead of `-1`. This holds on 29 February and, for a start on 29 February, on 28 February of a year without a leap day, in both directions. `duration in years of` and `duration in months of` a DateTime interval, and `CalculateAgeInYearsAt` and `CalculateAgeInMonthsAt` given a birth DateTime with a time of day, follow. The times of day are compared only as far as both values specify them, with seconds and milliseconds as one precision. Dates, and DateTimes without a time of day such as `ToDateTime(Patient.birthDate)`, give the same results as before, so `AgeInYears`, `AgeInYearsAt`, `AgeInMonths` and `AgeInMonthsAt` are unchanged. One such case does change: from a 29 February DateTime with a time of day to 28 February without one, `years between @2012-02-29T12:34:56 and DateTime(2014, 2, 28)` is `2` instead of `1`, the count it already gave on any other anniversary date. When one value specifies the time of day further than the other, as there, the count is taken at the coarser precision, which is one end of the uncertainty interval the specification defines for it (Language Semantics, "Determining Difference and Duration"): that case gives `[1, 2]`, and `years between @2012-03-10T22:30 and @2013-03-10T22` is `1` where the specification gives `[0, 1]`. The same goes for `AgeInYearsAt` and `AgeInMonthsAt` given a DateTime on the birthday, which count the year or the month as whole from the first moment of the birthday. Support for uncertainty is tracked in #132. (#1702, #1859)
- **Runtime** — `years between` counted backwards, from a later date to an earlier one, gave one year too many when either date is 29 February. It now gives the negative of the count forwards, as Appendix H of the CQL specification does for other dates, with 28 February as the anniversary of 29 February in a year without one (the note on Example 4.b). `years between @2012-02-29 and @2012-01-15` is `0` instead of `-1`, `years between @2016-02-29 and @2012-03-01` is `-3` instead of `-4`, `years between @2015-03-01 and @2012-02-29` is `-3` instead of `-4`, and `years between @2012-02-29 and @2012-02-28` is `0` instead of `-1`. This holds for Dates and DateTimes, and for `CalculateAgeInYearsAt` at a date before a birth on 29 February: `CalculateAgeInYearsAt(@2012-02-29, @2012-01-15)` is `0` instead of `-1`. Counting forwards, as an age at or after birth does, and `months between` are unchanged. (#1867, #1886)
- **Runtime** — a comparison of two values of different types that have no order between them, such as a Date and a DateTime, a Date and a Time, or an Integer and a Decimal, is `null` for `<`, `<=`, `>`, `>=`, `before` and `after`, instead of answering as if the left value were the greater: `A after B` and `B after A` were both true for a Date and a DateTime. `ICqlComparer.Compare` and `ICqlComparer.CompareValues` return `null` for such a pair instead of an order. Equality is unchanged: `=` is `false`, `!=` is `true` and `~` is `false` for such a pair, and lists and tuples whose elements differ in type are still unequal. ELM translated by this SDK does not hand these operators values of different types: the translator converts a Date compared with a DateTime with `ToDateTime` and an Integer compared with a Decimal with `ToDecimal`, and casts a value of a choice type to the operator's type. The change reaches ELM from another translator that leaves such a pair unconverted, and code that calls `ICqlOperators` directly. (#1649, #1861)
- **Runtime** — `singleton from` on a list with more than one element reports what went wrong. The message of LINQ's `SingleOrDefault`, "Sequence contains more than one element", did not name the CQL operator. The message names the operator, the number of elements and their CQL type, for example: "The singleton from operator requires a list with at most one element, but was given a list of 19 Condition elements. Use First or Last to take one element, or filter the list so that at most one element remains." (#1818, #1819)

**Code generator**

- **Code generator** — a library without a version, or with a version that isn't numeric such as `1.0.0-draft`, now compiles and can be invoked. One case still fails: a library without a version whose name contains a dash, when it refers to its own definitions, which #1540 tracks. The generated class always carries the two-argument `[CqlLibrary]`, with `null` for a missing version. `ILibrary.Version` returns `null` for such a library, declared `string?` in an annotations context of its own, so a checked-in file compiles with nullable on or off. The compiled assembly gets an `AssemblyVersion` only when the library's version consists of unsigned decimal parts, each below 65535. This raised `GeneratorToolVersion` to `6.2.1.0`. For a library with a numeric version, the generated C# is unchanged apart from that marker. (#1846, #1849)
- **Code generator** — a non-strict `as` whose operand is a value cast to a choice or to `Any` compiles when the value's own type cannot be the target, and evaluates to null, as the specification requires for a value of another type. `((@2024-01-01) as Choice<Date, DateTime>) after @2030-01-01T00:00`, and the same comparison with `before`, `>`, `<`, `>=` and `<=`, failed C# compilation with CS0039 ("Cannot convert type 'CqlDate' to 'CqlDateTime'"), so the whole library could not be evaluated; the comparison is now null. Other casts of that shape compile the same way, such as `(true as Any) as Decimal` and `('a' as Choice<String, Integer>) as Integer`. This raised `GeneratorToolVersion` to `6.2.2.0`. For a library that compiled before, the generated C# is unchanged apart from that marker. (#1869, #1879)
- **Code generator** — a `Concept` instance selector without a `display`, such as `Concept { codes: { Code { code: '1234-5', system: 'http://loinc.org' } } }`, now compiles. It evaluates to a `CqlConcept` with those codes and a null `display`, since an element that a selector leaves out is null. It used to fail with "No suitable constructor found for type Hl7.Cql.Primitives.CqlConcept." The generated C# passes `default` for the display to the existing two-argument constructor, so it also runs on earlier runtimes. C# generated for libraries that compiled before is unchanged, and so is `GeneratorToolVersion`. (#1808, #1856)
- **Code generator** — a `Concept` instance selector without `codes`, such as `Concept { display: 'Blood pressure' }`, now compiles, and so does the selector without any element, `Concept { : }`. It evaluates to a `CqlConcept` whose `codes` are null, with the display the selector gives or a null one. It used to fail with the same "No suitable constructor" error. The generated C# passes `default` for the codes to the existing two-argument constructor, so it also runs on earlier runtimes. C# generated for libraries that compiled before is unchanged, and so is `GeneratorToolVersion`. (#1857, #1875)
- **Code generator** — the build error for an element that a source's concrete type does not have no longer suggests casting the source with an explicit `as`, which cannot help there: `Property nonsense cannot be bound at compile time: Condition has no such element.` The hint stays for a source whose type is not known, abstract (such as `Resource`) or an interface, where a cast to a type that has the element makes the read bindable. (#1820, #1821)

**CQL-to-ELM translator**

- **A library-qualified identifier resolves as a query source, as retrieve terminology and as a retrieve context**, as it already did in an expression. `A."Encs" E`, `[Condition: A."VS"]` and `[A."Mother" -> Observation]` translate to an `ExpressionRef` or `ValueSetRef` with `libraryName` set, instead of reporting `Type  has no members`. This also holds when the include resolves from a reference library. A retrieve context is resolved as an identifier, so `["Mother" -> Observation]` references the expression `Mother`, and an unknown name there is reported. A model or library name on its own in these positions is now reported as it is in an expression. Before, it made translation throw, or went unreported. (#1733, #1837)
- **A library that defines a function twice with the same operand types** translates with the error `A function named Twice with the same type of arguments is already defined in this library.` on the second definition, which is dropped, instead of failing the whole library with an `ArgumentException`. Overloads with different operand types are unaffected. (#1843)
- **A DateTime literal with an hour, minute, second or offset out of range** (`@2014-01-01T25:00:00Z`) reports "Unparseable date/time literal" instead of failing translation with `ArgumentOutOfRangeException`, and one whose offset is 13 to 14 hours behind UTC (`@2014-01-01T10:00:00-13:30`) reports it instead of translating to a DateTime with that offset. A Time literal with an hour, minute or second out of range (`@T24:59:59.999`) reports "Unparseable time literal" instead of translating to a Time holding that component. (#1839, #1860)
- **The ELM JSON the translator writes carries `"fluent": true` on a fluent function**, so a library read back from that JSON keeps its fluent functions. (#1833, #1834)

### Upgrade Checklist

1. **Re-verify measure output.** A large number of fixes in this release move CQL evaluation results — overflow and unrepresentable results as `null`, the `ConvertsTo*` and `To*` conversions, `years between` and `months between` with a time of day or from 29 February backwards, comparisons of values of different types, `=` and `~` on Concepts, and the value set errors below among them. Treat moved scores for affected measures as expected rather than as new defects.
2. **Give your value set dictionary every value set your libraries reference.** A `ValueSetSource` without a terminology service, a `HashValueSetDictionary`, and the dictionary `FhirCqlContext.ForBundle` and `FhirCqlContext.WithDataSource` create when you pass none, now throw `CqlException<CqlUnresolvedValueSetError>` for a value set they do not hold, instead of answering `false`.
3. **Test codes with their system against a value set of several code systems.** A string, or a `Code` without a system, tested against such a value set throws `CqlException<CqlAmbiguousStringInValueSetError>`.
4. **Catch `CqlException` around evaluation**, or `catch (CqlException e) when (e.Error is ICqlEvaluationError)`, where you caught `ArgumentException`, `ArgumentOutOfRangeException`, `OverflowException`, `NotSupportedException` or `InvalidOperationException`. `CqlException.EvaluationFrames` names the definition the error was thrown in.
5. **If you name `CqlUcumYearArithmeticError`, `CqlUcumMonthArithmeticError` or `CqlPointFromNonUnitIntervalError`**, add `using Hl7.Cql.Primitives.Errors;` or `using Hl7.Cql.Operators.Errors;` and recompile. Read the properties of `CqlPointFromNonUnitIntervalError` instead of deconstructing it.
6. **Upgrade runtime and generated content together.** Libraries generated by 2.17.0 still load, since the invoker accepts `[6.0.0.0, 7.0.0.0)`, and regenerating them changes only the version marker. Do not ship what 2.18.0 packages to a host still on an earlier SDK.
7. **If you implement `ICqlOperators` yourself**, add `ConvertStringToRatio`, `ConvertsToRatio` and `ConvertRatioToQuantity`.
8. **If you compare FHIR concepts regardless of the order of their codings or of their display**, use `~` rather than `=`.
9. **If you parse strings yourself** with `CqlQuantity.TryParse`, `CqlRatio.TryParse`, `CqlDateTime.TryParse`, `CqlTime.TryParse`, `DateTimeIso8601.TryParse` or `TimeIso8601.TryParse`, or convert them with `FhirTypeConverter` or `ICqlOperators.Convert<T>`, pass them in the formats of the CQL `To*` conversions: quoted units, no surrounding whitespace, no group separators, and offsets within `-13:00` to `+14:00`.
10. **If you read `CqlAssemblyInfo.IsSupported` or `HasReadErrors`**, treat `CqlAssemblyWithNewerReferenceError` like any other `ReadError`.
11. **If you read `ILibrary.Version` or `CqlLibraryAttribute.Version` with nullable warnings enabled**, handle `null`.
12. **If you emit FHIR `Period`s from `Interval<DateTime>` values under an evaluation request that is not at UTC**, expect the exclusive end to carry the request's offset rather than `Z`.
13. **If you are on `net8.0`, plan the move to `net10.0`** — see the warning at the top of this document.
